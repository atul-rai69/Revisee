# Revisee refresh-token authentication

This document explains Revisee's rotating refresh-session design. It is both an
implementation guide and an operational checklist. It deliberately contains no
token, password, database URL, encryption key, or other secret value.

## Previous problem

Revisee previously issued one JWT access token at login and saved it in browser
`localStorage`. Angular attached that token to API requests. The JWT was
configured for a short lifetime (the tracked default was five minutes), while
the matching database login session was configured for 30 minutes. Deployments
could override the JWT value, which explains the observed logout at roughly 30
minutes. Regardless of the exact configured duration, there was no renewal
mechanism: after expiry, the interceptor treated the first `401` as final,
deleted the browser token, and sent the user to login.

Increasing the access-token lifetime would reduce those interruptions but would
also make a stolen bearer token useful for longer. A bearer token grants access
to whoever possesses it. Short-lived access tokens limit that exposure; a
separate, revocable refresh session provides continuity.

## Chosen architecture

- The access token is a JWT with `sub`, `sid` (refresh family), `iat`, `exp`,
  `type=access`, and a unique `jti`. Its default lifetime is 30 minutes. Angular
  keeps it only in memory and sends it as `Authorization: Bearer ...`.
- The refresh token is an opaque random value generated by Python's
  cryptographically secure `secrets.token_urlsafe`. It carries no trusted
  claims and is never returned in JSON.
- PostgreSQL stores only the token's SHA-256 hash. A database leak therefore
  does not directly reveal usable refresh tokens. The random token has enough
  entropy that offline guessing of its hash is impractical.
- The raw refresh token exists only in a `Secure`, `HttpOnly` cookie in
  production. Angular cannot read it, which reduces exposure to JavaScript and
  common token-stealing XSS payloads. XSS is still serious because malicious
  script can issue requests as the user.
- Every successful refresh consumes the current row and creates a replacement.
  Both rows share a random `family_id`; that chain is a token family.
- Presenting an already consumed or revoked token is replay/reuse. The backend
  revokes the entire family, clears the cookie, and requires a new login. The
  public error does not reveal whether theft was detected.
- Idle expiry limits how long the current token can go unused (default 14
  days). Absolute expiry limits the whole family (default 30 days), so repeated
  rotation can never create an immortal session.

The access token is not accepted by `/auth/refresh`, and an opaque refresh token
is not accepted by bearer-token authentication.

## Complete lifecycle

### Login and authorized requests

1. Angular posts credentials to `/login` with credentials enabled.
2. FastAPI verifies the password, creates a random family and refresh token,
   stores only the hash, and commits the session.
3. FastAPI sets the raw refresh token in an HttpOnly cookie and returns an
   access token, expiry seconds, and safe user data.
4. Angular holds the access token in memory and attaches it to protected API
   calls. The backend verifies its signature, type, expiry, user, and active
   refresh family.

```mermaid
sequenceDiagram
    participant B as Angular browser
    participant A as FastAPI
    participant D as PostgreSQL
    B->>A: POST /login (credentials)
    A->>D: verify user; insert refresh-token hash
    D-->>A: commit
    A-->>B: Set-Cookie HttpOnly + access token/user JSON
    B->>A: GET protected resource + Bearer access JWT
    A->>D: confirm user and active family
    A-->>B: protected response
```

### Expired access token, rotation, and retry

1. A protected request returns `401` with the safe response header
   `X-Auth-Error: access_token_expired`.
2. The interceptor joins or starts one shared `/auth/refresh` request. Login,
   registration, logout, refresh, and public requests never trigger this path.
3. FastAPI validates the request origin and `X-Revisee-CSRF` header, reads the
   HttpOnly cookie, hashes it, and locks its session row with `SELECT FOR UPDATE`.
4. In one transaction it validates idle/absolute expiry and user existence,
   consumes the old row, and creates exactly one replacement in the same
   family.
5. FastAPI replaces the cookie and returns a fresh access token.
6. Angular retries each waiting original request once. It does not recursively
   refresh a failed retry.

```mermaid
sequenceDiagram
    participant B as Angular interceptor
    participant A as FastAPI
    participant D as PostgreSQL
    B->>A: protected request (expired access JWT)
    A-->>B: 401 + access_token_expired
    B->>A: POST /auth/refresh (cookie + Origin + CSRF header)
    A->>D: lock current hash row
    A->>D: revoke current; insert replacement; commit
    A-->>B: rotated cookie + new access JWT
    B->>A: retry original request once
    A-->>B: success
```

### Browser reload and restoration

An Angular application initializer starts auth in `checking`, calls
`/auth/refresh`, and waits. A valid cookie rotates normally and restores both
the in-memory access token and user. A missing/expired cookie becomes
`unauthenticated` without a global application error. A network/server failure
becomes a separate recoverable `error` state. Guards wait for `checking` to end,
so they do not redirect during restoration.

### Logout and expiration

`POST /auth/logout` uses the cookie to revoke its complete family, then clears
the cookie with exactly the same name/path/SameSite/Secure attributes used to
set it. It is idempotent: a missing or unknown cookie is still cleared and
returns success. Angular clears all memory state in `finalize`, even if the
network request fails, then routes to login. Because bearer authentication also
checks for an active family, an access token from that logged-out family stops
working immediately.

When idle or absolute expiry is reached, refresh revokes the family and returns
an authentication failure. The user must log in again.

### Refresh-token reuse detection

If token A was rotated to token B and A appears again, FastAPI locks A, sees it
was consumed, revokes every row in the family (including B), clears the cookie,
and fails. This favors theft containment over silently accepting races.
Angular's single-flight behavior prevents same-tab races. Separate tabs share
the cookie but not JavaScript state; simultaneous cross-tab refreshes can
therefore trigger reuse defense and require login. Logout in one tab revokes the
server family, so other tabs are rejected on their next API call or refresh.

```mermaid
sequenceDiagram
    participant X as Client presenting old token A
    participant A as FastAPI
    participant D as PostgreSQL
    X->>A: POST /auth/refresh with consumed A
    A->>D: lock hash(A); observe revoked/replaced
    A->>D: revoke every row in A's family; commit
    A-->>X: 401 + expired refresh cookie
    Note over X,A: A new login is required; token B is no longer valid
```

Session restoration and logout are intentionally asymmetric: restoration may
issue a new session credential, while logout only revokes and removes one.

```mermaid
sequenceDiagram
    participant B as Angular browser
    participant A as FastAPI
    participant D as PostgreSQL
    alt Browser reload
        B->>A: POST /auth/refresh during app initialization
        A->>D: validate and rotate refresh session
        A-->>B: new cookie + access token/user
        B->>B: mark authenticated; release waiting guards
    else Manual logout
        B->>A: POST /auth/logout with cookie
        A->>D: revoke token family
        A-->>B: clear cookie + success
        B->>B: clear memory state; navigate to login
    end
```

## Backend implementation

### Database model and migration

Migration `20260927_0011_refresh_token_sessions.py` evolves the one existing
`user_sessions` table; it does not create a redundant session system. Important
columns are:

| Column | Purpose |
| --- | --- |
| `user_id` | Owning user; indexed and cascade-deleted with the user |
| `token_hash` | Unique SHA-256 hash; never the raw token |
| `family_id` | Indexed identifier shared across rotations |
| `parent_session_id` | Previous link in the rotation chain |
| `issued_at`, `created_at` | UTC issue/audit times |
| `expires_at` | Current token's idle expiry |
| `absolute_expires_at` | Hard family deadline inherited by replacements |
| `last_used_at` | Consumption time/evidence |
| `revoked_at` | Revocation or consumption time |
| `replaced_by_session_id` | Replacement link; also marks consumption |
| `user_agent` | Optional bounded diagnostic metadata (255 characters) |

The unique token hash prevents duplicate stored credentials. User, family, and
expiry indexes support authorization, family revocation, and cleanup. Rotation
uses a PostgreSQL row lock and one service-owned transaction; competing uses do
not create two valid children.

The legacy rows contain access-session IDs, not refresh hashes. Migration 0011
deletes only those obsolete session rows before changing the table. It does not
delete users or learning data, but all users must sign in once after rollout.
Downgrading likewise clears refresh-session rows because they cannot safely be
converted to the old format.

### Token, cookie, CORS, and CSRF responsibilities

- `src/core/security.py`: creates and validates access JWTs and enforces token
  type.
- `src/modules/auth/models.py`: authoritative refresh-session model.
- `src/modules/auth/repository.py`: locked lookup, active-family query, and
  family revocation.
- `src/modules/auth/service.py`: login/register issuance, hashing, transactional
  rotation, replay response, authentication, and logout revocation.
- `src/modules/auth/router.py`: safe response contracts, cookie lifecycle, and
  cookie-request CSRF checks.
- `src/core/config.py`: duration and cookie validation.
- `src/main.py`: exact credentialed CORS and safe auth-reason response header.

Production cookies use `HttpOnly=true`, `Secure=true`, `SameSite=None`, and
`Path=/auth`, with no `Domain`. Local HTTP development uses `Secure=false` and
`SameSite=Lax`. Cookie-authenticated refresh/logout requests require both an
exact `Origin` present in `CORS_ORIGINS` and the fixed non-simple
`X-Revisee-CSRF: spa` header. This is the selected CSRF strategy: an attacker
cannot add that header cross-origin without a successful trusted-origin CORS
preflight. A double-submit cookie was not used because the Vercel application
cannot read a token cookie scoped to the unrelated Render host. If both
services later move under a shared parent domain, a synchronizer/double-submit
design can be reconsidered.

## Angular implementation

- `core/services/auth.service.ts` owns the in-memory access token, user/status
  streams, credentialed login/register/refresh/logout calls, restoration, and
  one shared `shareReplay` refresh observable.
- `core/interceptors/auth-interceptor.ts` adds bearer authentication to normal
  API calls, recognizes only explicit access-expiry responses, joins the shared
  refresh, and retries once.
- `core/guards/auth-guard.ts` waits until initial restoration completes.
- `app.config.ts` starts restoration before normal navigation.
- Login and shell/sidebar logout handlers use the service's state lifecycle.

Angular cannot inspect the refresh token because `HttpOnly` removes it from
`document.cookie`. The browser attaches it only to matching credentialed
requests. The constructor removes the legacy `localStorage` access token during
the transition. No auth credential is put in local/session storage, IndexedDB,
application URLs, or persistent Angular state.

## API contracts

`POST /login` and `POST /register` preserve their JSON request bodies. Their
successful responses now include `expires_in` and `user` and set the cookie:

```json
{
  "access_token": "<JWT omitted>",
  "token_type": "bearer",
  "expires_in": 1800,
  "user": { "id": 1, "username": "name", "email": "address" }
}
```

Registration additionally includes its existing `message`. No JSON response
contains a refresh token, token hash, or family ID.

- `POST /auth/refresh`: empty JSON body; credentialed cookie request with trusted
  Origin and `X-Revisee-CSRF`; returns the login-shaped response and rotates the
  cookie.
- `POST /auth/logout`: empty JSON body with the same protections; returns
  `{ "message": "Logged out successfully" }` and expires the cookie.

The old root `/logout` contract is replaced by `/auth/logout` because the
cookie's intentionally restricted `/auth` path is not sent to the root route.

## Security decisions and remaining risk

This design reduces long-lived bearer theft, persistent token exposure to
JavaScript, useful database-token disclosure, replay, indefinite sessions,
CSRF on refresh/logout, and duplicate same-tab refresh rotation. Raw tokens
must never enter logs, exception bodies, analytics, URLs, or database columns.

A database leak exposes user/account data and token hashes, but not directly
usable random refresh tokens. A stolen raw refresh token can be used until its
idle/absolute expiry; rotation narrows that opportunity, and reuse of either
copy revokes the family. A stolen unexpired access token remains usable until
expiry unless the family is revoked first. HttpOnly does not solve XSS, browser
compromise, malicious extensions, CSRF bugs on other cookie endpoints, or
credential theft.

Credentialed CORS can never use `*`. Render must allow only the exact production
Vercel and approved custom origins. Some browsers/privacy modes block
third-party cookies between unrelated Vercel and Render sites even with
`SameSite=None`; a shared custom parent-domain arrangement is the most reliable
future production topology. Do not add a `Domain` attribute until such a domain
actually exists and has been reviewed.

## Configuration and deployment

### Required variable categories

Local backend `.env`:

- existing `SECRET_KEY`, database/provider/storage settings;
- `ACCESS_TOKEN_EXPIRE_MINUTES`;
- `REFRESH_TOKEN_IDLE_EXPIRE_DAYS`;
- `REFRESH_TOKEN_ABSOLUTE_EXPIRE_DAYS`;
- `AUTH_COOKIE_NAME`, `AUTH_COOKIE_SECURE=false`,
  `AUTH_COOKIE_SAMESITE=lax`, `AUTH_COOKIE_PATH=/auth`;
- exact localhost `CORS_ORIGINS`.

Render:

- the existing production secrets;
- the same duration/name/path variables;
- `AUTH_COOKIE_SECURE=true` and `AUTH_COOKIE_SAMESITE=none`;
- exact HTTPS Vercel/custom `CORS_ORIGINS`.

Vercel needs only the existing public `REVISEE_API_URL` pointing to Render. It
does not receive an auth secret or refresh token.

| Variable | Secret? | Role |
| --- | --- | --- |
| `SECRET_KEY` | Yes | Signs access JWTs; use the existing production secret-management process |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | No | Access JWT lifetime |
| `REFRESH_TOKEN_IDLE_EXPIRE_DAYS` | No | Maximum inactivity for the current refresh token |
| `REFRESH_TOKEN_ABSOLUTE_EXPIRE_DAYS` | No | Hard lifetime of a refresh family |
| `AUTH_COOKIE_NAME` | No | Browser cookie name |
| `AUTH_COOKIE_SECURE` | No | Requires HTTPS transport in production |
| `AUTH_COOKIE_SAMESITE` | No | `none` for the current cross-site deployment |
| `AUTH_COOKIE_PATH` | No | Restricted to `/auth` |
| `CORS_ORIGINS` | No | Exact trusted frontend origins; security-sensitive configuration |
| `REVISEE_API_URL` | No | Public Render API base URL compiled into Angular |

### Migration and verification

1. Back up/branch Neon and record the recovery target.
2. Deploy neither frontend nor backend yet. Review the pending migration and
   confirm the intended database without printing its URL.
3. From `backend`, run `.venv/Scripts/python.exe -m alembic current` and
   `.venv/Scripts/python.exe -m alembic heads`.
4. Rehearse `upgrade head`, `downgrade 20260920_0010`, then `upgrade head` only
   against a dedicated migration-test PostgreSQL database.
5. Schedule a short maintenance window and stop the old backend from serving
   writes: old application code expects the legacy session columns and is not
   compatible with schema 0011.
6. With explicit approval, apply `upgrade head` to the intended database.
7. Verify current reports `20260927_0011 (head)` and run
   `scripts/deployment_readiness.py`.
8. Deploy the new backend immediately with production cookie/origin variables,
   verify health/auth, end maintenance, then deploy the
   frontend. Existing users will sign in once because legacy session rows were
   intentionally discarded.

In browser DevTools, check that login's response has a Set-Cookie entry marked
HttpOnly/Secure/SameSite=None without copying its value. Confirm refresh sends a
cookie, returns 200 and a new access response, and sets a replacement cookie.
Use the Application cookie view to inspect attributes, never the token value in
screenshots or reports.

Rollback should normally deploy a forward fix. If an application rollback
cannot read the new schema, stop writes, roll back both frontend/backend, and
restore the reviewed Neon backup/branch. Alembic downgrade to 0010 intentionally
logs every user out and must be rehearsed and explicitly approved; it cannot
recover legacy session rows.

## Testing

Automated coverage includes:

- JWT lifecycle/type claims and access/refresh non-interchangeability;
- opaque refresh generation and hash-only persistence;
- login/registration response and cookie behavior;
- valid rotation, parent/replacement/family links, replay family revocation,
  idle/absolute expiry, explicit revocation, logout and idempotence;
- locked refresh lookup and the migration schema/index/foreign-key contract;
- exact Origin/custom-header CSRF rejection and production config validation;
- Angular credentialed login/refresh/logout, startup restoration, memory-only
  access tokens, guard waiting, one-time retry, single-flight refresh, auth-route
  exclusion, failed-refresh cleanup, and manual logout behavior.

Manual browser checklist:

- [ ] Login and inspect cookie attributes without revealing the value.
- [ ] Access a protected route and API.
- [ ] Use a very short access expiry in isolated development, wait, and confirm
      exactly one refresh and a successful original request retry.
- [ ] Reload on a protected route and confirm restoration before guard routing.
- [ ] Open multiple simultaneous API calls and confirm one refresh request.
- [ ] Logout; confirm cookie removal, protected UI removal, and rejected old
      bearer requests.
- [ ] Test missing, expired, and revoked cookies.
- [ ] Test Vercel-to-Render credentials/CORS in target browsers, including a
      privacy mode that may block third-party cookies.

Integration and migration tests require explicitly named disposable PostgreSQL
URLs and never fall back to the normal database. If those URLs are absent, the
tests are skipped rather than becoming unsafe. Browser verification also
requires a running migrated isolated backend; unit tests alone do not prove
real browser cookie policy.

## Interview learning summary

The problem was an access-token-only SPA: expiry always forced login. The design
keeps a short-lived bearer JWT in memory and a longer-lived opaque refresh token
in a Secure HttpOnly cookie. PostgreSQL stores only a hash and a rotation family;
each refresh transaction locks and consumes one token, while replay revokes the
family. Angular restores on startup, shares one refresh across concurrent 401s,
and retries each request once. The main tradeoffs are database work on auth,
forced login after legacy migration or replay, cross-tab race behavior, and
cross-site cookie reliability. These are preferred to long-lived JavaScript-
readable bearer credentials for Revisee's current Vercel/Render architecture.
